# Правила разработки

Нормативный документ. Пункты со словом «ошибка ревью» блокируют мерж.
Дополняет [architecture.md](architecture.md) (структура) и [legal-policy.md](legal-policy.md)
(юридические инварианты).

---

## 1. SOLID — как это применяется здесь

Принципы приведены не как теория, а как конкретные правила для этого кода.

### S — Single Responsibility

- Один use case = один файл = один класс = один публичный метод `execute`.
- Класс, который одновременно ходит в HTTP, пишет в БД и решает бизнес-правило — разбивается.
- Признак нарушения: в названии класса есть «And», или класс меняется по причинам из разных
  областей (изменился формат Open Library **и** изменилась логика дедупликации).

### O — Open/Closed

- Новый источник данных добавляется как **новая реализация** `BookMetadataProvider` плюс
  регистрация в composition root. Правка существующих use cases при этом не требуется.
- `switch (source)` внутри use case — ошибка ревью. Вместо этого — реестр провайдеров
  (`Map<ProviderId, BookMetadataProvider>`), заполняемый в `apps/*`.

### L — Liskov Substitution

- Любая реализация порта обязана соблюдать его контракт: не бросать «свои» типы ошибок мимо
  доменных, не возвращать `null` там, где контракт обещает пустой массив, не менять семантику
  идемпотентности.
- Контракт порта покрывается **общим набором тестов**: один test-suite прогоняется против всех
  реализаций порта (включая in-memory-фейк). Провайдер, не проходящий общий suite, не подключается.

### I — Interface Segregation

- Порты узкие и сценарные. `WorkRepository` не превращается в «Repository со всеми методами
  на все случаи»: если use case нужен только `findByNaturalKey`, он зависит от порта с этим методом.
- Толстый порт с 15 методами, из которых конкретный use case использует два, — ошибка ревью.

### D — Dependency Inversion

- Use case зависит от интерфейса из `domain`, не от класса из `infrastructure`.
- Все зависимости приходят через конструктор. `new PgWorkRepository()` внутри use case или
  импорт из `infrastructure` в `application` — ошибка ревью (проверяется линтером границ).
- Единственное место, где известны конкретные классы, — composition root в `apps/*`.

## 2. Идемпотентность

Система построена на предположении **at-least-once**: очередь может доставить задачу дважды,
клиент может повторить запрос, cron может пересечься сам с собой. Поэтому идемпотентность —
не оптимизация, а условие корректности.

### 2.1 Общее правило

> Повторное выполнение операции с теми же входными данными оставляет систему в том же
> состоянии, что и однократное, и возвращает тот же результат.

### 2.2 Запись в БД

- Любая вставка данных из внешнего источника — только `INSERT ... ON CONFLICT (natural_key)
DO UPDATE`. Голый `INSERT` для таких данных — ошибка ревью.
- **Natural key вычисляется детерминированно** из содержимого:
  - `work.natural_key = sha256(normalize(original_title) + '|' + normalize(author))`
  - `edition.natural_key = isbn13` либо `sha256(work_id|language|publisher|year|normalize(title))`
  - `source_link.url_hash = sha256(canonicalize(url))`
- `normalize()` (нижний регистр, схлопывание пробелов, удаление диакритики и пунктуации,
  транслитерация) — чистая функция в `domain`, покрытая табличными тестами. Её нестабильность
  ломает идемпотентность всей системы, поэтому менять её можно только с миграцией пересчёта ключей.
- `updated_at` обновляется только при фактическом изменении полей (сравнение перед записью),
  иначе метрика «актуальность» врёт.

### 2.3 Очереди

- `jobId` задаётся явно и детерминированно: `sync:{source}:{workId}:{YYYY-MM-DD}`. BullMQ
  отбросит дубликат сам.
- Обработчик не полагается на «задача выполнится один раз»: он обязан быть корректным при
  повторном запуске в любой момент, включая падение посередине.
- Все записи одной задачи — в одной транзакции (`UnitOfWork`). Частичного применения не бывает.

### 2.4 Мутирующие HTTP-эндпоинты

- `POST /api/sync/:source` требует заголовок `Idempotency-Key` (UUID клиента).
- Алгоритм: ищем `(key, endpoint)` в `idempotency_key` →
  - найдено и `request_hash` совпал → возвращаем сохранённый ответ, ничего не делаем;
  - найдено и `request_hash` отличается → `409 Conflict`;
  - не найдено → выполняем в транзакции вместе с сохранением ключа и ответа.
- TTL ключей — 24 часа, чистка отдельной джобой.

### 2.5 Импорт выгрузок (Фаза 2)

- Импорт разбит на батчи с чекпоинтом (номер строки/офсет) в `sync_log`. Перезапуск продолжает
  с последнего чекпоинта, повторная обработка батча безопасна за счёт upsert.

### 2.6 Чек-лист перед мержем операции записи

- [ ] Есть natural key или явный уникальный индекс, покрывающий конфликт.
- [ ] Указана стратегия `ON CONFLICT`.
- [ ] Запись атомарна (одна транзакция на логическую операцию).
- [ ] Есть тест «выполнить дважды → состояние и результат идентичны однократному».
- [ ] Ретрай после искусственного сбоя посередине не порождает дублей (тест).

## 3. Прочие обязательные принципы

### Явные границы (Ports & Adapters)

Внешний мир входит в систему только через порт. Прямой `fetch`, `pg`, `ioredis` вне
`packages/infrastructure` — ошибка ревью.

### Fail fast на входе, устойчивость на выходе

- Вход API валидируется Zod-схемой из `contracts` до попадания в use case; невалидный запрос
  падает сразу с `400`.
- Исходящие вызовы к источникам: таймаут (по умолчанию 5 с), до 3 ретраев с экспоненциальной
  задержкой и джиттером **только для идемпотентных операций**, circuit breaker на провайдер,
  соблюдение объявленных лимитов источника.

### Отказ одного источника не ломает ответ

Карточка книги отдаётся с данными доступных источников; недоступность WorldCat не превращается
в `500`. Деградация — частичные данные плюс отметка о неполноте, а не ошибка.

### Immutability в домене

Доменные сущности неизменяемы: изменение возвращает новый объект. Сеттеров нет.

### Явное над неявным

Никаких скрытых глобальных синглтонов, никакого чтения `process.env` вне слоя конфигурации.
Конфиг парсится Zod-схемой один раз при старте, невалидный конфиг = падение на старте.

### Отсутствие бизнес-логики в контроллерах и React-компонентах

Контроллер: валидация → вызов use case → маппинг в HTTP. Компонент: отображение. Правило
«показывать ли ссылку на скачивание» живёт в `domain`, а не в JSX.

### Детерминизм

Время и идентификаторы — только через порты `Clock` и `IdGenerator`. `Date.now()` и
`crypto.randomUUID()` внутри `domain`/`application` — ошибка ревью.

## 4. Код-стайл и типы

- TypeScript в `strict`, плюс `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`.
- `any` запрещён; `unknown` + сужение типа. Исключения — с комментарием и `eslint-disable` на строку.
- Публичные функции пакетов имеют явные возвращаемые типы.
- Ошибки: доменные ошибки — отдельные классы, наследники `DomainError`. Ловить и глотать
  исключение без логирования и без преобразования — ошибка ревью.
- Именование: файлы `kebab-case.ts`, классы `PascalCase`, функции/переменные `camelCase`,
  константы `UPPER_SNAKE_CASE`, порты `*.port.ts`, use cases `*.use-case.ts`, адаптеры
  `*.adapter.ts` / `*.repository.ts`.
- Комментарии объясняют «почему», а не «что». Закомментированный код не коммитится.
- Форматирование — Prettier, линт — ESLint; оба обязательны в CI.

## 5. Тестирование

| Уровень     | Что покрывает                                                            | Инструмент              | Где                                   |
| ----------- | ------------------------------------------------------------------------ | ----------------------- | ------------------------------------- |
| Unit        | Доменные правила, нормализация, `LinkPolicy`, use cases на фейках портов | Vitest                  | рядом с кодом                         |
| Contract    | Общий suite для всех реализаций порта, включая in-memory                 | Vitest                  | `packages/*/test/contract`            |
| Integration | Репозитории и очереди на реальных Postgres/Redis                         | Vitest + Testcontainers | `apps/api`, `packages/infrastructure` |
| E2E         | Сценарии «поиск → карточка → ссылки»                                     | Playwright              | `apps/web/e2e`                        |

Требования:

- Внешние HTTP-источники в тестах замоканы записанными ответами (фикстуры), сеть в CI не нужна.
- На каждую операцию записи — тест идемпотентности (двойной прогон).
- На `LinkPolicy` — тесты, доказывающие, что ссылка на теневую библиотеку и прямое скачивание
  copyrighted-издания невозможны (см. `legal-policy.md`).
- Покрытие: `domain` и `application` ≥ 90 %; общий порог CI ≥ 80 %.
- Новый баг чинится вместе с тестом, воспроизводящим его.

## 6. Работа с внешними источниками

- Каждый источник — отдельный адаптер, отдельная очередь, отдельный circuit breaker.
- Ключи и лимиты — из конфигурации, никогда из кода.
- Ответы источников кэшируются на уровне адаптера (Redis, TTL по источнику), чтобы ретрай и
  соседняя джоба не тратили лимит дважды.
- User-Agent содержит имя проекта и контакт — этого требует этикет публичных API (Open Library).
- Условные запросы (`If-None-Match` / `If-Modified-Since`) используются везде, где источник их
  поддерживает.
- Скрейпинг HTML запрещён во всех случаях (см. `legal-policy.md`).

## 7. Git и процесс

- Ветки: `main` — всегда деплоится; работа в `feat/*`, `fix/*`, `chore/*`, `docs/*`.
- Коммиты — Conventional Commits (`feat(api): add editions endpoint`), на английском.
- Мерж в `main` только через PR с зелёным CI: `lint`, `typecheck`, `test`, `build`,
  проверка границ слоёв.
- PR ≤ ~400 строк диффа; больше — разбить.
- Изменение архитектурного решения = ADR в `docs/adr/` в том же PR.
- Миграции БД только вперёд (`db:generate` → ревью SQL → `db:migrate`). Ручная правка
  применённой миграции запрещена.
- Секреты не коммитятся; `.env.example` актуализируется вместе с изменением конфига.

## 8. Definition of Done для задачи

- [ ] Код соответствует направлению зависимостей из `architecture.md`.
- [ ] Логика в нужном слое; порты не обойдены.
- [ ] Операции записи идемпотентны, чек-лист §2.6 пройден.
- [ ] Тесты нужных уровней написаны и проходят локально.
- [ ] `pnpm lint && pnpm typecheck && pnpm test` зелёные.
- [ ] Публичный API описан в `contracts` и попал в OpenAPI.
- [ ] Документация обновлена, если изменился контракт или архитектура.
- [ ] Легальная политика не нарушена (§ `legal-policy.md`), тесты политики проходят.
