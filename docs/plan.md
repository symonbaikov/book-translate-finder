# План реализации BookTranslate Finder

План разложен на фазы из исходного брифа с добавлением технического каркаса, без которого
Clean Architecture и идемпотентность не получится соблюсти «потом». Каждая фаза заканчивается
проверяемым результатом.

Связанные документы: [architecture.md](architecture.md) · [rules.md](rules.md) ·
[legal-policy.md](legal-policy.md).

**Обозначения:** ✅ сделано · 🚧 в работе · ⬜ не начато. Текущий статус проекта: Фаза 1.0
завершена, активная фаза — Фаза 0 (разведка данных) параллельно с началом Фазы 1.1.

---

## Обзор

| Фаза | Название            | Оценка     | Главный результат                                                   |
| ---- | ------------------- | ---------- | ------------------------------------------------------------------- |
| 0    | Прототип-разведка   | 1–2 недели | Доказано, что открытых API хватает для продукта                     |
| 1.0  | Каркас монорепо     | 3–5 дней   | Слои, границы, CI, Docker — до первой бизнес-логики                 |
| 1    | MVP                 | 3–4 недели | Своя нормализованная БД, синхронизация, UI, Docker-деплой           |
| 2    | Расширение покрытия | 3–5 недель | WorldCat, Index Translationum, диплинки заимствования, CI/CD на AWS |
| 3    | Публичный запуск    | 2–3 недели | Open-source релиз, документация, мониторинг                         |

Приоритет — Фазы 0 и 1: они проверяют гипотезу и дают работающий MVP без источников, требующих
долгого согласования доступа.

## Фаза 0 · Прототип-разведка (1–2 недели)

**Цель:** проверить гипотезу на минимальном UI без своей БД. Главный вопрос — достаточно ли
полны и полезны данные Open Library и Google Books, чтобы продукт имел смысл.

**Чем эта фаза отличается от остальных:** здесь допустимо срезать углы. Прототип живёт в
`prototype/`, не проходит проверку границ слоёв и **выбрасывается** в конце Фазы 1. Единственное
правило, которое действует и здесь, — легальная политика.

### Задачи

- ⬜ `prototype/` — страница поиска на Next.js без бэкенда, прямые запросы к API из клиента.
- ⬜ Тонкая обёртка над Open Library API (search + editions + languages).
- ⬜ Тонкая обёртка над Google Books API (метаданные, ISBN, ссылка на покупку).
- ⬜ Вывод списка языков перевода и ссылок на archive.org / Gutenberg для public domain изданий.
- ⬜ Ручная разметка правового статуса ссылок (заготовка будущей `LinkPolicy`).

### Разведка данных (главная ценность фазы)

- ⬜ Взять выборку из 50 книг: 20 классика/public domain, 20 современных бестселлеров,
  10 нишевых нон-фикшн.
- ⬜ Для каждой зафиксировать: сколько языков перевода нашлось, сколько изданий, есть ли ISBN,
  указан ли переводчик, есть ли легальная ссылка.
- ⬜ Записать результат в `docs/research/coverage-phase0.md`.
- ⬜ Замерить реальные лимиты и латентность обоих API, зафиксировать формы ответов как фикстуры
  для будущих тестов (пригодятся в Фазе 1).
- ⬜ Отдельно оценить качество поля «переводчик» — по опыту это самое дырявое поле, и от него
  зависит ценность карточки.

### Definition of Done

- [ ] Кликабельный прототип: ввод «название + автор» → список языков и ссылок.
- [ ] Отчёт `coverage-phase0.md` с числами по 50 книгам.
- [ ] Принято решение по цели «≥ 70 % известных книг находят ≥ 3 перевода»: достижима, требует
      Фазы 2, или гипотезу надо пересматривать.
- [ ] Сохранён набор фикстур ответов источников.

### Выход/стоп-условие

Если по выборке медиана языков перевода < 2 и Google Books не добирает — до старта Фазы 1
пересматриваем нишу либо сразу закладываем WorldCat/Index Translationum в MVP. Решение
фиксируется в ADR.

## Фаза 1.0 · Каркас монорепо (3–5 дней)

**Цель:** создать структуру, в которой правила из `rules.md` соблюдаются автоматически.
Делается **до** бизнес-логики: границы слоёв, добавленные задним числом, не приживаются.

### Задачи

- ✅ pnpm workspaces: `apps/{web,api,worker}`, `packages/{domain,application,infrastructure,contracts}`.
- ✅ TypeScript strict + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`, общий
  `tsconfig.base.json`, project references (`apps/web` — отдельно, свой tsconfig под Next.js).
- ✅ ESLint + Prettier; **проверка границ импортов** (`pnpm boundaries` → dependency-cruiser):
  `domain` без зависимостей, `application` не видит `infrastructure`, `web` не видит
  `infrastructure`/`application`/`domain`. Проверено экспериментом: намеренное нарушение
  (`application` → `infrastructure`, с объявленной зависимостью) падает; `eslint-plugin-boundaries`
  не резолвил такие импорты в этом стеке и был исключён (см. [ADR-0001](adr/0001-clean-architecture-monorepo.md)).
- ✅ Vitest: unit + contract + integration-проекты, Testcontainers для Postgres/Redis (проверено
  живым прогоном — реально поднимает контейнеры).
- ✅ `docker/docker-compose.dev.yml`: Postgres, Redis, healthcheck. `docker/app.Dockerfile` —
  параметризованный multi-stage build для api/worker (`pnpm deploy`), собран и проверен вживую
  для обоих приложений.
- ✅ Слой конфигурации: Zod-схема окружения (`loadEnv`/`baseEnvSchema` в infrastructure, свои
  расширения в api/worker/web), падение на старте при невалидном конфиге с читаемым списком
  всех ошибок сразу (проверено), `.env.example`.
- ✅ Скелет NestJS на Fastify: `/health/live`, `/health/ready`, pino с `correlationId`
  (`X-Correlation-Id` из запроса или сгенерированный), глобальный фильтр доменных ошибок
  (`DomainError` → 400/404/409, всё остальное → непрозрачный 500).
- ✅ CI на GitHub Actions: `lint → boundaries → typecheck → test → test:integration → build`,
  сводная джоба `ci` как единая точка для required-статуса.
- ✅ Скрипты из «контракта команд» в [CLAUDE.md](../CLAUDE.md) работают (проверены вживую, включая
  `pnpm dev` для всех трёх приложений одновременно).

### Definition of Done

- [x] `pnpm install && pnpm dev` поднимает три приложения локально (api :3001, worker, web —
      проверено живым прогоном, включая health-эндпоинты и рендер страницы).
- [x] Умышленный импорт из `infrastructure` в `application` роняет CI (`pnpm boundaries`).
- [x] `pnpm test:integration` поднимает контейнеры (Postgres + Redis через Testcontainers) и
      проходит.

Фаза 1.0 закрыта 2026-08-12. `db:generate`/`db:migrate`/`db:seed` и `pnpm sync` — намеренные
заглушки с понятным сообщением до Фазы 1.2/1.3, не «пустые» реализации.

## Фаза 1 · MVP (3–4 недели)

**Цель:** своя нормализованная база вместо запросов к API на лету. Работающий сервис,
задеплоенный в Docker-контейнере.

### 1.1 Домен и модель данных

- ⬜ Сущности `Work`, `Edition`, `SourceLink`, VO `Isbn`, `LanguageCode`, `RightsStatus`, `LinkType`.
- ⬜ Функция `normalize()` и вычисление natural keys (детерминированность — под тестами).
- ⬜ `LinkPolicy` со всеми инвариантами и тестами из [legal-policy.md](legal-policy.md).
- ⬜ Правила слияния изданий и приоритета источников при конфликте полей.
- ⬜ Порты: репозитории, `BookMetadataProvider`, `UnitOfWork`, `CachePort`, `JobQueuePort`,
  `Clock`, `IdGenerator`, `IdempotencyStore`.
- ⬜ In-memory реализации портов + общий contract-test-suite для них.

### 1.2 Хранилище

- ⬜ Drizzle-схема: `work`, `edition`, `source_link`, `language`, `external_ref`, `sync_log`,
  `idempotency_key`.
- ⬜ Уникальные ограничения по natural key и `(source_name, external_id)` — основа идемпотентности.
- ⬜ `CHECK`-ограничение на нелегальные комбинации `type`/`is_legal_free`.
- ⬜ Индексы: trigram по названию и автору, `(work_id, language)`, partial unique по ISBN-13.
- ⬜ Первая миграция, сид справочника языков ISO 639-1.
- ⬜ Postgres-реализации репозиториев с `ON CONFLICT DO UPDATE` + integration-тесты, включая
  тест «двойной прогон не создаёт дублей».

### 1.3 Источники и синхронизация

- ⬜ `OpenLibraryProvider` и `GoogleBooksProvider`: таймауты, ретраи с джиттером, circuit breaker,
  уважение rate limit, кэш ответов на уровне адаптера, условные запросы.
- ⬜ Use case `SyncWorkFromSource`: нормализация → дедупликация изданий → `LinkPolicy` → upsert
  в одной транзакции → `sync_log` → инвалидация кэша.
- ⬜ BullMQ: очередь на источник, детерминированный `jobId`, DLQ для упавших задач.
- ⬜ Cron `RefreshStaleWorks`: обновление активных записей не реже раза в неделю.
- ⬜ Дедупликация изданий: ISBN-13 → нормализованные (язык, издатель, год, название).
- ⬜ **Lazy backfill** ([ADR-0003](adr/0003-lazy-backfill.md)): промах поиска ставит задачу
  наполнения; отдельная очередь с пониженным приоритетом, схлопывание одинаковых запросов
  по `jobId`, кэш отрицательных результатов (TTL 24 ч), лимиты на постановку. Без этого
  свежая self-host инсталляция бесполезна.

### 1.4 API

- ⬜ `GET /api/search`, `GET /api/works/:id`, `GET /api/works/:id/editions`,
  `GET /api/editions/:id/links`.
- ⬜ Состояние `202 pending` у `GET /api/search` для lazy backfill: статус, `pollAfterMs`,
  описание в OpenAPI.
- ⬜ `POST /api/sync/:source` с обязательным `Idempotency-Key`, служебным токеном и семантикой
  повторов (тот же ответ / `409` при другом теле).
- ⬜ Zod-схемы в `packages/contracts`, генерация OpenAPI.
- ⬜ Redis-кэш ответов с версионированным префиксом и явной инвалидацией по `work_id`.
- ⬜ Базовый rate limiting по IP.

### 1.5 Web

- ⬜ Страница поиска с подсказками и списком кандидатов.
- ⬜ Карточка книги: языки перевода, список изданий, фильтр по языку и году.
- ⬜ Блок ссылок с явными бейджами «public domain» / «купить» / «взять в библиотеке» (И-4).
- ⬜ Состояния: загрузка, пусто, частичные данные при недоступности источника.
- ⬜ Состояние «ищем в источниках…» для `202 pending` с опросом и разумным таймаутом.
- ⬜ SSR карточки для SEO, базовая доступность (a11y).

### 1.6 Docker и self-hosting

Self-hosting — целевой сценарий, не побочный эффект контейнеризации
(см. [architecture.md §9](architecture.md#9-развёртывание-и-self-hosting)).

- ⬜ Multi-stage Dockerfile для api, worker, web: непривилегированный пользователь, минимальный
  финальный слой, без dev-зависимостей.
- ⬜ Корневой `docker-compose.yml` для self-host: postgres, redis, migrate, api, worker, web;
  healthcheck у каждого сервиса, именованные volume для данных.
- ⬜ Миграции — **отдельный one-shot сервис** `migrate`; api и worker стартуют через
  `depends_on: service_completed_successfully`. Никаких миграций в entrypoint приложения.
- ⬜ `.env.example` со всеми переменными и пометкой обязательности; валидация конфига Zod при старте.
- ⬜ Опциональный профиль `tls` с Caddy и автоматическим Let's Encrypt.
- ⬜ Сборка multi-arch образов (`amd64`, `arm64`), публикация в GHCR с семантическим тегом.
- ⬜ Проверка «чистая машина»: `git clone` → `cp .env.example .env` → `docker compose up -d` →
  рабочий поиск, без единой ручной команды сверх этого.
- ⬜ Замер потребления ресурсов простаивающего стека; цель — уложиться в 2 vCPU / 2 ГБ RAM.
- ⬜ Документированные процедуры обновления (`pull && up -d`) и бэкапа (`pg_dump` + проверка
  восстановления).
- ⬜ Структурные логи в stdout со сквозным `correlationId`, метрики инструментированы
  (экспорт — Фаза 3).

### Definition of Done

- [ ] Ответ пользователю формируется **только** из своей БД, синхронных походов во внешние API
      из HTTP-обработчика нет (backfill идёт через очередь).
- [ ] Повторный запуск синхронизации по одной работе не меняет данные и не создаёт дублей (тест).
- [ ] Сценарий первого запроса на пустой инсталляции покрыт E2E: `202` → ожидание → `200`.
- [ ] Прототип из Фазы 0 удалён.
- [ ] Покрытие `domain` и `application` ≥ 90 %, общее ≥ 80 %.
- [ ] Все тесты легальной политики зелёные.
- [ ] Сторонний человек разворачивает инстанс на чистой машине по README за три команды
      (проверено на живом человеке, не на авторе).
- [ ] Замеры: холодный кэш ≤ 2 с, тёплый ≤ 300 мс на выборке из Фазы 0.

### Явно НЕ входит в Фазу 1

Аккаунты пользователей, избранное, рекомендации, мобильное приложение, WorldCat,
Index Translationum, мультирегиональные диплинки.

## Фаза 2 · Расширение покрытия (3–5 недель)

**Цель:** повысить полноту данных и добавить редкие языки. Каждый новый источник — новая
реализация существующего порта, без переписывания use cases (принцип Open/Closed на практике).

### Задачи

- ⬜ Запрос доступа к WorldCat Search API (учрежденческий ключ) — **начать в начале Фазы 1**,
  согласование долгое и блокирует старт этой фазы.
- ⬜ `WorldCatProvider` как реализация `BookMetadataProvider`; проходит общий contract-suite.
- ⬜ Импорт выгрузок Index Translationum: батчи с чекпоинтами в `sync_log`, перезапуск
  продолжает с последнего чекпоинта, повтор батча безопасен.
- ⬜ Сопоставление исторических записей Index Translationum с существующими `work` (matching
  по нормализованным полям, ручная проверка выборки на качество склейки).
- ⬜ Диплинки на легальное заимствование (Libby/OverDrive, Open Library Lending) с учётом региона.
- ⬜ Региональные диплинки на покупку — партнёрские программы опционально, при этом раскрытие
  партнёрского статуса обязательно.
- ⬜ Приоритеты источников при конфликте полей, отражение источника факта в UI.
- ⬜ CI/CD на GitHub Actions: сборка образов, автодеплой на AWS, откат по тегу.
- ⬜ Управление секретами (AWS Secrets Manager / SSM), ротация ключей источников.
- ⬜ Нагрузочный тест поиска и карточки, оптимизация индексов по результатам.

### Definition of Done

- [ ] Подключены минимум 3 источника, каждый — отдельный адаптер, use cases не менялись при
      добавлении (проверяется по диффу).
- [ ] Повторное измерение полноты на выборке Фазы 0: рост доли книг с ≥ 3 переводами; цель ≥ 70 %.
- [ ] Импорт выгрузки переживает убийство процесса посередине и корректно продолжается.
- [ ] Пуш в `main` автоматически доводит изменение до окружения, откат отработан на учениях.

### Риски фазы

Доступ к WorldCat могут не дать или дать с жёстким лимитом. План Б: Index Translationum +
национальные библиотечные каталоги с открытыми API. Фаза не должна блокироваться целиком на
одном источнике.

## Фаза 3 · Публичный запуск (2–3 недели)

**Цель:** открытый релиз проекта как open-source, готового принимать внешних контрибьюторов.

### Задачи

- ⬜ README: что за проект, скриншоты, быстрый старт, **явная декларация легальной политики** (И-5).
- ⬜ Публичная документация API (OpenAPI + человеческое описание, примеры запросов).
- ⬜ `CONTRIBUTING.md` с прямым запретом PR на интеграции с теневыми библиотеками,
  `CODE_OF_CONDUCT.md`, шаблоны issue/PR.
- ⬜ Лицензия MIT; проверка лицензионной чистоты зависимостей.
- ⬜ Мониторинг: Prometheus + Grafana — латентность, hit-rate кэша, длина очередей, ошибки и
  остаток лимитов по источникам, возраст устаревших записей; алерты на исчерпание лимитов.
- ⬜ Публичный статус-дашборд и `/health` для внешних проверок.
- ⬜ **Self-host релиз:** раздел «Запусти у себя» в README, публикация версионированных
  multi-arch образов в GHCR, матрица совместимости версий образа и схемы БД, changelog с
  явной пометкой миграций, ломающих обратную совместимость.
- ⬜ Публикуемый seed-дамп популярного ядра каталога (`pnpm db:seed:catalog` / профиль compose):
  снимает эффект холодного старта у новой инсталляции. Состав дампа проверяется на
  соответствие [legal-policy.md](legal-policy.md) — только метаданные и легальные ссылки.
- ⬜ Тест обновления: инсталляция версии N обновляется до N+1 без потери данных (прогон на CI).
- ⬜ Аудит безопасности перед открытием репозитория: история коммитов без секретов, аудит
  зависимостей, заголовки безопасности, CORS, лимиты.
- ⬜ Политика приватности и раскрытие партнёрских ссылок, если они появились в Фазе 2.
- ⬜ Открытие репозитория, релиз `v1.0.0`, анонс.

### Definition of Done

- [ ] Сторонний разработчик поднимает проект локально по README без вопросов к автору
      (проверено на живом человеке).
- [ ] В истории репозитория нет секретов (проверено сканером).
- [ ] Дашборды и алерты работают на реальном трафике.
- [ ] Легальная политика видна в README, `CONTRIBUTING.md` и в UI.

## Критерии успеха MVP

| Критерий          | Целевое значение                                               | Как измеряем                                           |
| ----------------- | -------------------------------------------------------------- | ------------------------------------------------------ |
| Полнота данных    | ≥ 70 % запрошенных известных книг находят ≥ 3 перевода         | Прогон по выборке из Фазы 0, отчёт в `docs/research/`  |
| Скорость ответа   | холодный кэш ≤ 2 с, тёплый ≤ 300 мс                            | p95 из метрик API                                      |
| Актуальность      | фоновая синхронизация не реже раза в неделю на активные записи | Метрика максимального возраста `synced_at`             |
| Легальная чистота | 0 прямых ссылок на скачивание вне public domain источников     | Тесты `LinkPolicy` + периодический аудит `source_link` |

## Сквозные риски

| Риск                                                | Влияние                                                | Митигация                                                                                                            |
| --------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
